ZK Intuition

Analogy: Imagine proving you know a secret passphrase to enter a cave — without ever revealing the passphrase itself.

  • Prover convinces a Verifier that a statement is true.
  • The verifier learns nothing beyond the truth of the statement.
  • Properties: Completeness, Soundness, Zero-Knowledge.
Use the "Ali Baba cave" analogy. Completeness = honest prover always convinces. Soundness = cheating prover fails. ZK = verifier learns nothing extra. Ask students: "Can you think of a real-world situation where you prove something without revealing it?" (e.g., age verification without showing ID).

SNARK vs STARK (High Level)

SNARKs

  • Small proof size (~200 bytes)
  • Fast verification
  • Requires trusted setup
  • Not quantum-resistant

STARKs

  • Larger proofs (~50-200 KB)
  • Transparent (no trusted setup)
  • Quantum-resistant (hash-based)
  • Higher verification cost on-chain

Many production systems use a hybrid: STARK internally, SNARK wrapper for cheap L1 verification.

Don't go deep into math here. Key takeaway: SNARKs are compact but need trust assumptions; STARKs are transparent but bigger. The industry is converging on hybrid approaches. Ask: "Why might you wrap a STARK inside a SNARK?"

Recursion & Aggregation

  • Recursion: a proof that verifies another proof — "proof of a proof".
  • Aggregation: combine many proofs into one succinct proof.
  • Why it matters:
    • Prove thousands of transactions in a single on-chain verification.
    • Enables tree-structured parallelism in proving.

Mental model: Imagine folding a long receipt into a single stamp of approval.

Recursion is the key to scalability. Without it, proving cost grows linearly with batch size. With recursion, you build a tree: each leaf proves a chunk, inner nodes aggregate, and the root is what goes on-chain. Draw a binary tree on the whiteboard if possible.

Proof vs Witness

Witness

The private input — all the data the prover uses to compute the proof (execution trace, state, etc.).

Never sent on-chain. Can be very large.

Proof

The succinct output — a short cryptographic object that convinces the verifier.

Posted on-chain. Tiny relative to the witness.

Analogy: the witness is the full exam paper with your working; the proof is just the final grade certificate. The verifier (L1) only sees the certificate. Ask students to identify which is the bottleneck: generating the witness or computing the proof? (Answer: both, but witness generation is often underestimated.)

EVM-Equivalence Intuition

  • EVM-compatible: runs Solidity, but may differ in edge cases.
  • EVM-equivalent: behaves exactly like Ethereum's EVM — same opcodes, gas, precompiles.
  • Why it matters: existing contracts, tools, and tests work unchanged.

The zkEVM must prove every opcode faithfully — making the circuit design much harder but the developer experience seamless.

Emphasize the spectrum: Type 1 (fully equivalent) → Type 4 (high-level language compatible). Most production zkEVMs aim for Type 2 or 2.5. The closer to Type 1, the harder the circuits but the better the compatibility. Ask: "What breaks if you skip a rarely-used opcode?"

📚 Background — Crypto Building Blocks

Essential primitives that underpin all zero-knowledge systems.

Transition slide. This section covers the cryptographic and data-layer foundations. 10 minutes.

Hashes & Merkle Trees

Hash Functions

  • Deterministic, one-way, collision-resistant
  • ZK-friendly hashes: Poseidon, Rescue
  • Used everywhere: commitments, Fiat-Shamir, Merkle roots

Merkle Trees

  • Commit to large datasets with a single root
  • Prove membership with O(log n) path
  • Ethereum state = giant Merkle Patricia Trie
Ask students if they've used git — git is a Merkle DAG. Poseidon is preferred in ZK circuits because it's ~100x cheaper to prove than SHA-256 inside a circuit. Draw a simple 4-leaf Merkle tree and show how you verify one leaf.

Circuits & Arithmetization (Intuitive)

  • A circuit is a program expressed as math constraints (additions & multiplications over a finite field).
  • Arithmetization = turning computation into polynomial equations the proof system can check.
  • Think of it as: "compile your program into algebra".

Example: Proving x * y = z where z is public but x, y are secret → one multiplication gate, one constraint.

Don't go into R1CS or PLONKish details here — just build intuition. The key insight: any computation can be broken into simple add/multiply gates. The prover fills in all the wire values (witness), and the proof system checks that every gate's constraint holds without revealing the values. A zkEVM circuit has millions of gates — one for every opcode step.

Data Availability vs Validity

Data Availability (DA)

  • Can anyone reconstruct the full state?
  • Rollups post data to L1 (calldata / blobs)
  • Without DA, even valid proofs are useless — you can't exit

Validity Proofs

  • Is the state transition correct?
  • ZK proofs guarantee correctness
  • Verified on-chain by a smart contract

A zk-rollup needs both: validity (proof) + data availability (posted data).

Common misconception: "ZK rollups don't need data availability." They do! Without DA, users can't prove their balances to exit. Validity proofs ensure correctness; DA ensures liveness and user sovereignty. Optimistic rollups flip this: they assume validity and use fraud proofs + DA.

Motivations

  • Security: cryptographic validity over social trust.
  • Scalability: compress execution verification cost.
  • Composability: preserve EVM developer experience.
  • Finality UX: predictable settlement windows.
  • Cost control: optimize proving + calldata footprint.
Frame tradeoffs: you gain stronger correctness guarantees but pay for complexity in proving systems and operations.

Prover Market

  • Emerging model: open prover marketplace with scoring + staking/slashing.
  • Requirements:
    • Deterministic job specs
    • Proof validity checks + anti-equivocation
    • Reputation and reliability metrics
  • Roadmap should begin permissioned, then progressively open.
Emphasize market design risks: cartelization, latency gaming, and unreliable providers. Stress phased liberalization.

Prover Architectures

  • Monolithic prover: simpler coordination, weaker elasticity.
  • Modular pipeline: specialized stages, better parallelism.
  • Recursive proving trees: aggregate many subproofs into one final proof.
  • Hardware strategy: CPU baseline + GPU acceleration (+ optional FPGA/ASIC roadmap).

Selection criteria: latency target, capex/opex profile, failure isolation, and upgrade complexity.

Discuss architecture as business decision too: cost predictability, vendor dependence, and operational resilience.

Real-Time Proving

  • Target class: near-real-time proofs for user-facing finality expectations.
  • Levers:
    • Parallel witness generation
    • Precompilation/circuit specialization
    • Aggressive batching + adaptive block sizing
  • Need graceful degradation when proof queue backlogs.
Call out SLO mindset: P50/P95 proving latency, queue depth, and drop/fallback policies.

Integration Challenges

  • EVM edge-case compatibility and opcode semantics drift.
  • State model alignment across execution, witness, and verifier.
  • Bridges/oracles introducing non-zk trust dependencies.
  • Versioning pain: circuit upgrades vs client/protocol upgrades.
  • Observability gaps across proving pipeline stages.
Practical warning: most delays happen in integration, not core proving math. Instrument early and test adversarially.

Security

  • Threats: circuit bugs, faulty witness generation, key compromise, malformed proofs.
  • Controls: multi-implementation verification, formal methods on critical circuits, independent audits.
  • Operational security: signer isolation, deterministic builds, reproducible prover binaries.
  • Response: emergency brakes + rollback/fallback playbooks.
Treat zk stack as high-assurance software plus critical infra. Mention drills, incident readiness, and segmented privileges.

Rollout Plan (2026)

  • Phase 0: private devnet, synthetic load tests.
  • Phase 1: guarded testnet with partner provers.
  • Phase 2: capped mainnet beta + strict risk limits.
  • Phase 3: progressive decentralization of proving and governance.

Exit criteria per phase: correctness, latency SLOs, cost envelope, and incident readiness.

Highlight explicit go/no-go gates. No phase should advance based on narrative momentum alone.

🧪 Demos & Hands-On Exercises

Demo 1: ZK Proof Visualization INTERACTIVE

Goal: Visually understand what a proof "looks like" and how verification works.

  • Open zkp.science interactive demos
  • Walk through the "3-coloring" graph proof
  • Observe: each round reveals partial info but never the full solution
  • After ~20 rounds, the verifier is convinced

💡 Discussion: Why does the verifier need multiple rounds? What happens if the prover cheats?

TEACHER INSTRUCTIONS: 1. Open zkp.science in a browser (or use the Sudoku ZK demo at https://zk-sudoku.vercel.app if preferred). 2. Explain: the prover has a valid 3-coloring of a graph. The verifier picks a random edge each round. 3. The prover reveals the colors of that edge's endpoints (but shuffles color labels each round). 4. If any edge has same color → prover is caught cheating. After k rounds, cheating probability ≤ (1-1/m)^k. 5. Key insight: the verifier never sees the full coloring — that's the "zero knowledge" part. 6. Let students try: ask one to be the prover (with a solution on paper) and another to be the verifier picking edges. 7. Debrief: connect this to blockchain — the L1 verifier contract plays the verifier role, but non-interactively (Fiat-Shamir).

Demo 2: Toy Prover Simulation HANDS-ON

Goal: Run a minimal proof system end-to-end on your laptop.

  • Use snarkjs with a simple circuit: a * b === c
  • Steps: write circuit → compile → generate witness → create proof → verify
  • Observe proof size vs witness size
# Install
npm i -g snarkjs circom

# Compile circuit (multiplier.circom)
circom multiplier.circom --r1cs --wasm --sym

# Generate witness  (input.json: {"a":"3","b":"11"})
node multiplier_js/generate_witness.js multiplier_js/multiplier.wasm input.json witness.wtns

# Trusted setup + prove + verify
snarkjs groth16 setup multiplier.r1cs pot12_final.ptau circuit.zkey
snarkjs groth16 prove circuit.zkey witness.wtns proof.json public.json
snarkjs groth16 verify verification_key.json public.json proof.json
TEACHER INSTRUCTIONS: 1. Pre-install snarkjs and circom on the lab machines OR have students use a Gitpod/Codespace with them pre-installed. 2. Provide the multiplier.circom file: `template Multiplier() { signal input a; signal input b; signal output c; c <== a * b; } component main = Multiplier();` 3. Provide input.json: {"a":"3","b":"11"} → public output c should be 33. 4. Walk through each step. Pause at "trusted setup" to explain: this is the ceremony step SNARKs need. 5. After proof generation, have students run `ls -la proof.json witness.wtns` to compare sizes. 6. Key observation: witness is much larger; proof is tiny. That's succinctness. 7. Bonus: change input to wrong values and show verification fails. 8. Time: ~15 min if pre-installed, ~25 min if installing from scratch.

Demo 3: Merkle Proof Exercise HANDS-ON

Goal: Build and verify a Merkle proof by hand, then connect it to ZK state proofs.

  • Construct a 4-leaf Merkle tree on paper (or whiteboard)
  • Leaves: H("Alice:100"), H("Bob:50"), H("Carol:75"), H("Dave:200")
  • Generate a membership proof for Bob's balance
  • Verify: given root + proof path, confirm Bob has 50

💡 Extension: What if Bob tries to claim he has 500? Why does it fail?

TEACHER INSTRUCTIONS: 1. Draw a 4-leaf binary Merkle tree on the whiteboard. Label leaves L0-L3 with the hash of each account string. 2. Compute interior nodes: N01 = H(L0 || L1), N23 = H(L2 || L3), Root = H(N01 || N23). 3. Bob's proof path: sibling L0 (= H("Alice:100")) + sibling N23. Proof size = 2 hashes. 4. Verification: recompute H(L0 || L1) using provided sibling + Bob's leaf, then H(result || N23), check against root. 5. Ask: "If Bob lies about his balance, which hash changes?" → His leaf hash changes → the recomputed root won't match. 6. Connect to zkEVM: Ethereum's state trie is a Merkle Patricia Trie. The zkEVM must prove correct state transitions over this structure. 7. Optional code demo: use ethers.js `keccak256` to compute the hashes live. 8. Time: ~10 min.

Demo 4: Prover-Market Auction Simulation ROLE-PLAY

Goal: Experience prover market dynamics through a classroom auction game.

  • Divide class into Provers (3-5) and one Sequencer
  • Sequencer posts a "block" (difficulty + deadline + reward)
  • Provers bid: price + estimated time
  • Sequencer selects winning bid; simulate proof delivery
  • Track reputation scores across 3 rounds

💡 Twist in round 3: one prover "fails" to deliver — what happens?

TEACHER INSTRUCTIONS: 1. Setup: assign 3-5 students as provers, 1 as sequencer, rest as observers/scorekeepers. 2. Round 1: Sequencer announces Block A — difficulty: LOW, deadline: 5 min, reward: 10 tokens. Provers write bids on paper (price they'd accept + time estimate). Sequencer picks lowest price with reasonable time. 3. Round 2: Block B — difficulty: HIGH, deadline: 2 min, reward: 25 tokens. Observe how bids change. 4. Round 3: Block C — one pre-selected prover "wins" but then announces "proof failed / timed out." Sequencer must re-auction. Discuss: slashing, reputation damage, fallback strategies. 5. Debrief questions: What prevents cartel behavior (all provers agreeing on high prices)? How do you balance speed vs cost? What's the minimum number of provers for a healthy market? 6. Connect to real systems: Taiko, Scroll, and zkSync's prover selection mechanisms. 7. Time: ~15 min.

Demo 5: End-to-End zkEVM Transaction Trace WALKTHROUGH

Goal: Trace a single transaction from submission to finality on a zkEVM.

  1. User sends tx → Sequencer includes in batch
  2. Execution trace generated (all opcodes + state changes)
  3. Witness builder extracts private inputs
  4. Prover computes proof over the trace
  5. Recursive aggregator bundles with other batch proofs
  6. Final proof submitted to L1 verifier contract
  7. L1 confirms validity → batch is finalized ✅
TEACHER INSTRUCTIONS: 1. Use a block explorer for a live zkEVM (e.g., https://explorer.zksync.io or https://scrollscan.com). 2. Find a recent finalized batch. Click into it and show: batch number, proof tx on L1, number of L2 txs included. 3. Walk through each step on the slide, mapping it to what you see on the explorer. 4. Key observations: (a) Time between L2 tx and L1 finality — this is the proving latency. (b) Gas cost of the verify tx on L1 — this is shared across all txs in the batch. (c) The L1 verify tx calls a verifier contract — show the contract on Etherscan. 5. Ask: "If proving takes 10 minutes and the batch has 1000 txs, what's the per-tx proving cost?" 6. Optional deep-dive: show the verifier contract source code — it's surprisingly short because the math is in the precompiles. 7. Time: ~10 min.
